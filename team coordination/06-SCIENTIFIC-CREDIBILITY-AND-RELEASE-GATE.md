# Shared scientific credibility and release gate

Read [architecture33](../architecture%20files/33-SCIENTIFIC-CREDIBILITY-AND-CLAIM-GATES.md) before implementing a conclusion, scientific status, critic action or export. This gate supplements each person's owned tests. It is mandatory for the combined app, including a local synthetic build. No coding agent can satisfy it by adding disclaimers while retaining unsupported green results.

| Deliverable | Producer | Consumer and required check |

Tanush owns shared contracts and migrations as before. Ayan owns scientific configuration/implementation. Aradhya owns presentation and the pure renderer. Missing contract fields follow the existing change-request process; do not invent parallel JSON shapes or edit another person's code to get a temporary pass.

## Required checkpoint additions

- F0: C1 domain/OpenAPI including `AnalogPassport.assurance_evidence_id`; assurance schema, gate IDs and export-bundle port types; scientific policy/adequacy receipt models; platform negative contract fixtures. Full scientific computation may still be unavailable.
- S0: analytic oracles, typed adequacy evidence and independent verifier baseline. Demonstrate actual insufficient scale/coverage becoming UNKNOWN, not just a handcrafted status response.
- U0: all disposition/status combinations, evidence/uncertainty display and a clearly labeled incomplete assurance state. Missing audit is never a success badge.
- S1: actual product decoding/scale/lineage controls, bounded discovery controls and source-validation manifest. Distinguish executed replay/download from unrun access.
- U1/P1: actual audited bundle renders in browser and HTML/JSON/CSV; all attempts and essential unknowns survive export/reload. No mock fallback.
- RC: exact integrated commit passes the tests below; release report records capability scope and unrun external gates. Main advances only to the tested candidate.

SC gate outcomes and SCI test outcomes are different concepts. Tests must pass when the correct scientific answer is FAIL, UNKNOWN, GAP or INCONCLUSIVE. Never weaken a test to manufacture positive science.

## Real-data credibility evidence

For each required Earth/Mars/Moon source path supply actual product/version, exact granule/asset identifiers and checksums, relevant label metadata, body/frame/units, acquisition/support, mask/valid fractions, transformations, algorithm/parameter versions and at least one reproduced derived observable. Capture actual outcome and limits. An empty-source or no-coverage test demonstrates correct handling; it does not demonstrate a successful real-source comparison.

Keep tuning and held-out controls distinct in versioned scenario manifests. Lock their membership before tuning. Expected qualitative behavior needs independent physical reasoning and actual evidence, not agreement with a known site's name. NASADEM and SRTM sharing ancestry cannot be used to manufacture independent validation. For limited time, a small well-documented real experiment is preferable to broad unsupported claims, while the full required feature scope remains tracked as unfinished until implemented.

Use [scientific-validation-report.template.json](templates/scientific-validation-report.template.json). All entries start NOT_RUN. Include exact tested source SHA, policy/algorithm/source locks, executed test command/exit counts, actual source receipts, control split, audited passport IDs and blockers. A stage is PASSED only after its applicable checks ran and evidence exists. BLOCKED_EXTERNAL/SKIPPED/NOT_IMPLEMENTED remain explicit. S5 physical validation remains NOT_IMPLEMENTED for the baseline.

## Merge and release decision

Owned pure software/science tests and consumer contracts must pass before their branch merges. The combined integrity/UI/export matrix above must pass before product acceptance. A branch may merge with an external live-source gate blocked only if no implemented capability or release statement falsely claims it passed; record the blocked gate and remediation. This does not satisfy full real-data release acceptance.

Local offline acceptance and scientifically demonstrated real-data capability are separate release scopes. A limited local app may run while credentials are absent; it must say so. Claiming full science readiness requires G4/S3 and the applicable modeled experiment S4 evidence from26/29. Live-agent readiness separately requires G6. None authorizes a physical rover safety/readiness claim.

No unknown should disappear when combining branches. Tanush compares UI, API, assurance JSON and exported passport for the same frozen run; Aradhya checks rendering; Ayan checks scientific interpretation. Release observations belong to the exact tested integration SHA. A later change to algorithms, policy, sources or claim presentation invalidates the affected checks and requires rerunning them.
