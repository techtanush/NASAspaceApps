# Tanush scope and file ownership

Own every durable application boundary: configuration, identity, accepted mission/rover records, run lifecycle, jobs, evidence registration, tool/role execution, policy, public HTTP and integration. Your work makes Ayan's computed results and Aradhya's interface part of one traceable system.

## Production scope

- Python package/root settings and CLI; all Pydantic/domain/status/quantity types; RFC8785 hashes and semantic validators.
- PostgreSQL/PostGIS models, migrations, repositories and workspace-scoped transactions. You are the only migration writer.
- Mission drafts/autosave, preparation jobs, acceptance, rover imports/revisions and frozen run creation.
- Run actions, selected candidates/portfolios, review records, durable snapshots/events, idempotency and revision guards.
- Content-addressed storage, acquisition/derivation registration, lineage closure, checksums, authorized artifact/export reads.
- PostgreSQL queue/leases/fencing/retries/cancellation; CPU subprocess orchestration and safe progress events.
- All ten runtime Agent Council roles, common policy, strict schemas, provider adapter, tool registry and proposal policy. A role's name is not a separate model service.
- Application wrappers for qualification, compatibility, verification and portfolios that call Ayan's pure facade and persist validated results.
- Passport manifest/claim assembly and asynchronous export endpoint; call Aradhya's pure renderer for presentation bytes.
- Dependency/runtime locks, Compose/Make/bootstrap/identity/security/operations and final cross-branch integration.

Exact paths are in shared ownership registry. Your broad `analogforge/` default does not override Ayan/Aradhya's more specific prefixes. Do not edit their owned modules just because your import fails; report the missing interface or fix your adapter. A joint approved integration patch is recorded and tested.

## Shared interfaces you must publish

F0 supplies typed ports, domain/API schema and safe context. Later changes require a contract-change record and consumer regeneration/retest. Publish actual exported OpenAPI and scenario IDs; do not leave the frontend guessing `scenario_config_id`, draft retrieval, selected state or missing read endpoints. Preserve the43 initial API operations unless an explicit reconciled architecture change updates them.

Ayan owns numerical outputs. Your wrapper verifies evidence references, units, scope and algorithm identity, but must not recalculate route energy in a second incompatible way. Aradhya owns frontend request/response usage and generated TypeScript; you own the Python source API and exported OpenAPI. Aradhya owns the pure passport renderer; you supply the frozen report bundle, authorization and storage.

## Test ownership

Own platform/domain/API/DB/jobs/agent/policy tests, integration tests and fixture seeds for durable flows. Ayan's numerical suites remain his responsibility; Aradhya's browser/accessibility/renderer suites remain hers. At final integration you execute all of them and diagnose issues with the producer. A passing platform fake-facade test cannot be claimed as actual science integration.

## Explicit exclusions

Do not rewrite frontend components, scientific leaf packages, source decoders or their dependency choices without coordination. Do not introduce Redis/Celery/SQLite or another provider stack to avoid implementing the chosen design. Do not deploy/publish/create GitHub resources or control hardware as part of this local build. Do not collect keys from teammates' unrelated files or assume their coding tools supply live product credentials.

## Definition of your completed responsibility

Your branch individually is ready when F0/platform/agent tests pass, stable interfaces are delivered, no unsafe bypasses exist and your implementation has honest missing-module behavior. The **team product** is complete only after actual Ayan/Aradhya modules merge and full integrated gates pass. State those two statuses separately in the handoff.
